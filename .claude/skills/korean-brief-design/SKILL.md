# 한국어 기획안 문서화

한글 기획안은 개조식으로 쓰인다. □ 아래 ○, 그 아래 -, 또 그 아래 ·. 이 스킬은 그
내용을 두 가지 그릇 중 하나에 담는다. **원문을 읽는 방식은 같고, 담는 그릇만 다르다.**

## 1. 산출물 형식을 정한다

| 쓰임 | 형식 | 읽을 문서 |
|---|---|---|
| 공문서, 정식 보고서, 결재·배포용 | **HWPX** | `references/hwpx.md` |
| 회의 설명, 공유 링크, 발표 | **HTML** | 아래 4~6절 + `references/components.md` |

확실치 않으면 묻는다. 한국 조직에서 정식 문서는 결국 한글 파일로 나가고, 소개·공유는
링크가 편하다. 같은 내용을 둘 다 만들어 달라는 경우도 흔하다 — 그때는 아래 2·3절의
읽기 작업을 한 번만 하고 그릇만 두 번 만든다.

## 2. 용도에 따라 밀도를 정한다

같은 내용이라도 쓰임에 따라 깊이가 달라진다.

- **회의 논의용** — 참석자가 각자 자료를 들고 오는 자리. 구조와 컨텐츠만 앞에 세우고
  운영 세부는 붙임으로 민다. 뎁스가 깊으면 아무도 안 읽는다.
- **공유·홍보용** — 혼자 스크롤하며 읽는다. 서사를 만든다.
- **설계 검토용** — 판단 근거가 핵심. 대안 비교와 도식, 계산이 중심.

## 3. 개조식을 읽고 그릇을 정한다

이게 이 스킬의 본체다. 원문을 훑으며 각 덩어리가 무엇인지 판정한다. 판정은 형식과
무관하고, 결과를 담는 그릇만 달라진다.

| 원문의 모습 | HWPX | HTML |
|---|---|---|
| □ 대제목 | □ 스타일 | 섹션 (eyebrow + h2) |
| ○ 나열형 사실 (일시·장소·규모·주최) | **표** (구분/내용) | **표** |
| ○ 시각이 붙은 순서 (12:30~, 13:00~) | **표** (시간/내용) | **타임라인** (mono 시각 + 색 노드) |
| ○ 여러 안을 저울질 | **표** | **비교표** — 권장안 행만 강조 |
| ○ 목표 수치 (300건, 200명) | 표 또는 ○ 문장 | **수치 타일** |
| ○ 시기별 할 일 | **표** (시기/마일스톤) | **표** |
| ○ 위험과 대응 | **표** | **표** (리스크/시점/대응) |
| ○ + 하위 - 여러 개가 결국 한 논지 | **한 문장으로 압축** | **한 문장으로 압축** |
| · 4단계 항목 | 상위에 흡수하거나 표 셀로 | 없앤다 |
| 공간·자리 배치 설명 | 글로 설명 | **평면도 SVG** (`references/diagrams.md`) |

**개조식 뎁스는 어느 형식이든 2단까지만.** 종이에서도 화면에서도 4단 들여쓰기는
계층이 아니라 소음이다.

압축은 내용을 버리는 게 아니다. "A이다 / 근거는 B / 사례는 C"처럼 한 논지가 세 줄로
늘어져 있으면 한 문장으로 합치는 것이지 C를 지우는 게 아니다. 숫자·고유명사·날짜는
그대로 옮긴다.

## 4. HTML 경로 — 스타일을 입힌다

`assets/tokens.css`를 `<style>`에 통째로 붙이고 시작한다. 매번 토큰을 다시 짜지
않는다. 마크업 골격은 `references/components.md`에 있다.

색의 역할이 정해져 있다.

- **코발트** — 주 액센트. 섹션 번호, 링크, 주요 항목, 수치.
- **앰버** — 문서에서 **가장 중요한 축 하나**에만. 차별화 포인트, 최대 리스크,
  전환 지점. 여기저기 쓰면 강조가 사라진다.
- **초록/붉은색** — 좋음/경고의 의미색. 액센트를 대신하지 않는다.

글꼴은 세 역할로 나눈다. **Gothic A1**(제목, 800~900), **IBM Plex Sans KR**(본문),
**IBM Plex Mono**(시각·수치·라벨). 숫자가 세로로 정렬돼야 하는 곳에는
`font-variant-numeric: tabular-nums`를 빠뜨리지 않는다.

라이트·다크는 세 상태로 대응한다 — 명시적 라이트, 명시적 다크, 그리고 **아무
스탬프도 없는 시스템 기본**. 토큰 파일이 이미 그 구조이니 색을 미디어쿼리 안에서만
새로 정의하지만 않으면 된다. `body` 배경도 반드시 토큰으로 칠한다.

## 5. HTML 경로 — 제목과 발행

`<title>`은 설명이 아니라 이름이다. "AAIA 2026 연말 행사 기획안 소개자료"가 아니라
"에이전트, 일을 시작했다". 두세 단어의 고유한 이름을 붙이고, 설명은 발행할 때
`description`에 넣는다. 같은 문서를 고칠 때는 **같은 파일 경로로 다시 발행**해
URL을 유지한다.

## 6. 도식은 필요할 때만

공간 배치, 시간 구조, 상태 전환 — 이 셋이 아니면 대개 표가 낫다. 그릴 때는
`references/diagrams.md`를 읽는다. 테마 대응, `<defs>`/`<use>` 재사용, 축척, 그리고
**캡션에 "왜 이 배치인가"를 적는 규칙**이 거기 있다.

## 7. 한국 실무 문서의 관례 (공통)

기획안은 대개 확정 전 문서다. 표시가 없으면 읽는 사람이 가정을 사실로 오해한다.

- 확정되지 않은 수치에는 **(안)** 을 붙인다. "등록 목표 300건(안)".
- 초안이면 그 사실을 문서에 밝힌다. HWPX는 ※ 단서로, HTML은 푸터에 DRAFT 배지로.
- 가상 인물·기업이 등장하는 시뮬레이션이면 실재하지 않음을 명시한다.
- 작성 주체·작성일을 넣고, 한글 문서는 끝에 "끝."을 오른쪽 정렬로 둔다.

**내가 만들어 넣은 가정값은 사용자에게 따로 알린다.** 원문에 없던 수치를 조용히
채우면 나중에 회의에서 사고가 난다.

## 하지 말 것

- **원문을 그대로 옮기지 않는다.** 개조식 불릿을 `<ul>`로 바꾸기만 한 페이지나,
  나열형을 목록 그대로 둔 한글 문서는 이 스킬을 쓴 게 아니다. 표로 읽혀야 할 것을
  표로 만드는 게 일이다.
- **확정된 서식 수치를 눈대중으로 바꾸지 않는다.** `assets/styles.report.json`의
  값은 실제 문서에서 측정한 것이다. 사용자가 새 수치를 주면 그때 바꾼다.
- **번호를 아무 데나 매기지 않는다.** 01/02/03은 실제로 순서가 의미를 가질 때만.
  병렬 항목에 번호를 붙이면 없는 순서를 지어내는 셈이다.
- **모든 요소에 애니메이션을 걸지 않는다.** 한 화면에 들어오는 카드가 하나씩
  떠오르면 산만하다. 섹션당 한 무리면 충분하다.
- **원문에 없던 주장을 만들지 않는다.** 구조를 바꾸는 것과 내용을 지어내는 것은
  다르다. 빈칸이 보이면 채우지 말고 묻는다.
- 이모지를 섹션 표지로 쓰지 않는다. 파비콘 외에는 쓸 자리가 거의 없다.

## 번들 파일

```
scripts/hwpx_generator.py     HWPX 생성기 (표준 라이브러리만 사용)
assets/styles.report.json     확정된 스타일 수치 + 제목 표 템플릿 + 표 서식
assets/content.example.json   내용 JSON 예시
assets/tokens.css             HTML 디자인 토큰 + 기본 컴포넌트
references/hwpx.md            한글 문서 경로 — 수치표, 실행법, 서식 추출, 검증
references/components.md      HTML 마크업 골격
references/diagrams.md        SVG 도식 규약
```

## 유래

AAIA 2026 연말 행사 기획 작업(2026.8)에서 정리했다. 참조 한글 문서에서 서식을
추출해 생성기를 만들고, 같은 내용을 소개페이지·세션 상세·시뮬레이션·배치 설계
네 개의 HTML로도 냈다. 두 형식의 규칙이 여기 함께 들어 있다.
